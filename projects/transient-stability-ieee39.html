Transient Stability Detection on the IEEE 39-Bus System

Machine-learning classifiers trained on DIgSILENT PowerFactory simulation data to decide whether the IEEE 39-bus (New England) system stays stable after a disturbance. The best-performing model reached 99.82% accuracy with an ROC-AUC of 0.9999.

Project overview

This is the final project for the S.Tr.T Teknologi Rekayasa Elektro programme at Sekolah Vokasi Universitas Gadjah Mada. The goal was to replace a slow, repeated time-domain stability assessment with a trained classifier that can label a post-disturbance operating condition as stable or unstable almost instantly.

The IEEE 39-bus New England test system was used as the study case because it is a widely accepted benchmark, which makes the method reproducible and comparable with published work.

✅

Tooling note: DIgSILENT PowerFactory is used only in this final project, purely as the source of simulation data. The Neera and Lombok studies in this portfolio were built in ETAP.

Problem statement

Classical transient stability assessment relies on running a dynamic time-domain simulation for every contingency and operating point. That is accurate but computationally heavy, so it does not scale well to online or near-real-time screening.

The question this project answers is simple: can a supervised model, trained on a large set of simulated disturbance scenarios, reproduce the stable / unstable verdict accurately enough to be useful as a fast screening layer?

Scope & my role

  • Built and validated the IEEE 39-bus model in DIgSILENT PowerFactory as the data-generation environment.
  • Designed the scenario matrix (loading conditions, fault locations, fault clearing times) that defines the dataset.
  • Ran the batch of dynamic simulations and exported the resulting operating-condition data.
  • Labelled each scenario as stable or unstable based on the simulated generator rotor-angle behaviour.
  • Prepared the dataset in Python: cleaning, feature preparation, and train / test splitting.
  • Trained, tuned, and compared Random Forest and XGBoost classifiers.
  • Evaluated the models with accuracy, precision, recall, F1-score, and ROC-AUC, then documented the full workflow in the final report.

Method & workflow

  1. Build the benchmark model. Assemble the IEEE 39-bus system in PowerFactory and verify the base-case load flow against the published benchmark data.
  2. Define the scenario matrix. Vary loading level, fault location, and clearing time so the dataset covers both comfortably stable and clearly unstable operating points.
  3. Run the simulation batch. Execute the dynamic simulations and export the measured quantities that describe each operating condition.
  4. Label the outcomes. Classify each scenario as stable or unstable from the generator rotor-angle response after fault clearing.
  5. Prepare the dataset. Clean the exported data, assemble the feature table, check the class balance, and split into training and testing sets.
  6. Train and tune. Fit Random Forest and XGBoost classifiers and tune the main hyperparameters.
  7. Evaluate and compare. Score both models on the held-out test set using accuracy, precision, recall, F1, and ROC-AUC, then select the best performer.
  8. Document. Write up the methodology, results, and limitations as the final project report.

Lessons learned

  • The quality of the scenario matrix matters more than the choice of algorithm — coverage of the operating space is what makes the classifier generalise.
  • Very high scores deserve scepticism. Checking the train / test split for leakage and confirming that unstable cases are genuinely represented was an essential sanity step.
  • Combining a power-system simulation tool with a Python ML pipeline is a practical workflow, and the data export / labelling bridge is where most of the engineering effort actually goes.
  • Documenting assumptions early made the final report far easier to defend.
